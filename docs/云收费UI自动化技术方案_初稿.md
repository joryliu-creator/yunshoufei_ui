# 云收费 UI 自动化技术方案及问题清单（初稿）

## 1. 文档目的

本文用于说明云收费 UI 自动化的技术实现方式、AI 在自动化建设中的使用边界、跨环境复用方案、当前已实现的场景、通过脚本发现的问题。

## 2. 项目背景

此前使用 MeterSphere 进行接口自动化时，接口脚本和多环境参数需要较多手工维护。当业务规则、测试数据或环境地址发生变化时，需要重复修改脚本和配置，影响回归效率。

当前采用“AI 辅助设计和编码 + 自动化框架执行 + 测试人员审核”的方式建设 UI 自动化。目标是由测试人员提供业务流程、测试数据和验收标准，由 AI 快速生成或调整可维护的自动化代码，再由框架稳定执行。

## 3. 技术选型与整体架构

### 3.1 技术栈

| 层次 | 技术/实现 | 主要职责 |
|---|---|---|
| AI 辅助层 | AI 编程助手 | 分析业务流程、生成页面对象、补充断言、辅助定位失败原因 |
| 编程语言 | Python | 编写测试脚本、数据处理和业务辅助逻辑 |
| UI 驱动 | Playwright | 驱动 Chromium，操作真实 DOM，支持 iframe、弹窗、等待、截图和 trace |
| 测试框架 | pytest | 组织用例、参数化、fixture、标记、收集和报告 |
| 页面封装 | Page Object | 集中封装页面定位器和页面操作，测试用例只编排业务流程 |
| 数据管理 | Excel + 环境配置 | Excel 管理回归场景和业务参数，环境文件管理环境差异 |
| 执行调度 | Jenkins/Windows 任务计划/Docker | 支持定时回归、服务器执行和报告归档 |
| 结果产物 | HTML、JUnit、截图、trace、JSONL 日志 | 支持结果查看、失败复盘和问题定位 |

### 3.2 执行链路

```text
业务流程、验收标准、测试数据
              ↓
       AI 辅助分析与编码
              ↓
 Excel 场景配置 + 环境配置 + Page Object
              ↓
       pytest 用例编排
              ↓
       Playwright 浏览器执行
              ↓
金额/状态/账期/唯一编号/清理结果断言
              ↓
      HTML、JUnit、截图、trace、日志
```

### 3.3 当前代码分层

- `src/pages/`：页面对象和页面操作，包括门户、账单中心、计费出账、临时台账、客户管理等。
- `tests/`：按业务模块组织测试用例，通过 pytest fixture、参数化和标记控制执行。
- `src/config/`：环境、账号角色、客户及 Excel 测试数据的加载和校验。
- `src/domain/`：周期类、电表类等计费公式和业务计算逻辑。
- `scripts/`：登录态保存、前置数据准备、账单清理、报告生成和回归执行入口。
- `artifacts/`：测试报告、截图、trace、实时执行日志和失败证据。

## 4. 多环境复用方案

同一套测试代码通过运行参数选择环境，不在测试脚本中硬编码环境地址、客户编号或账号密码：

```powershell
python -m pytest tests/billing `
  --test-env standard1 `
  --customer-id <客户编号> `
  --account-role default
```

环境差异通过以下文件或参数管理：

```text
.env.standard1
.env.standard2
.env.uat
.env.prod.example
```

账号密码、验证码、Cookie 和登录态不进入代码、Excel 或 Git，统一从本地安全配置或 Jenkins Credentials 获取。

“一套代码多个环境复用”不代表环境之间完全不需要维护。可复用的是测试流程、页面对象和断言逻辑；环境地址、客户数据、账号权限、前置数据和少量页面差异由配置或适配层处理。

建议将差异分为三类：

1. 配置差异：通过环境文件、命令行参数和 Jenkins 参数解决。
2. 数据差异：通过 Excel 场景配置、映射表和前置数据模板解决。
3. 产品差异：通过 Page Object 的定位策略或少量环境适配方法解决，避免在每条测试用例中复制分支代码。

## 5. AI 在自动化建设中的使用方式

### 5.1 适合交给 AI 的工作

- 将人工操作步骤转换为 Python + Playwright 代码。
- 生成或补充 Page Object 页面方法。
- 将重复场景参数化，减少复制粘贴。
- 根据失败截图、trace 和日志分析定位问题。
- 补充金额、账期、状态、唯一编号和数据清理断言。
- 根据页面结构变更同步修改脚本、Excel 用例和说明文档。
- 生成测试数据模板、执行命令和回归报告整理内容。

### 5.2 必须由测试人员确认的内容

- 业务流程是否正确，不能仅以页面提示成功作为通过依据。
- 计费公式、折扣、账期、金额和状态的预期结果。
- 测试数据归属、账号权限和环境范围。
- 创建、作废、删除等有副作用操作是否允许执行。
- 清理目标是否唯一，是否可能误伤其他测试数据。
- 失败原因属于产品缺陷、环境问题、数据问题还是自动化脚本问题。

AI 生成的代码必须经过代码评审和真实环境验证后，才能进入正式回归。AI 不应直接拥有生产环境创建、作废或删除数据的权限。

## 6. 自动化与产品 Skill 同步沉淀

UI 自动化建设不仅用于执行回归，也可以在梳理页面流程和确认验收结果的过程中，持续补齐产品原有文档不足的问题，形成可复用的产品 Skill 和业务知识资产。

### 6.1 可沉淀的产品资产

- 业务入口：账单中心、计费出账、临时台账等入口的适用范围和边界。
- 业务规则：周期类、仪表类、临时类、押金类等收费类型的计算方式、状态流转和数据归属。
- 页面规则：房间树、收费项树、日期控件、弹窗、iframe 等复杂控件的正确操作顺序。
- 验收规则：金额、账期、收费项、账单状态、唯一编号和清理结果等关键断言。
- 数据规则：前置数据准备、客户房间迁入、测试数据生命周期和安全清理要求。
- 问题知识：已确认的产品缺陷、修复结论、版本差异和回归注意事项。

### 6.2 沉淀流程

```text
人工操作/业务讨论
        ↓
AI 辅助整理流程、规则和断言
        ↓
测试人员在真实页面验证
        ↓
产品或业务人员确认业务含义
        ↓
同步更新自动化脚本、Excel 用例和产品 Skill
        ↓
形成可复用的产品知识资产
```

### 6.3 资产价值

- 补齐产品没有形成正式文档的隐性业务规则。
- 降低新成员理解产品和设计用例的成本。
- 让 AI 后续生成脚本时拥有稳定、统一的业务上下文。
- 避免业务规则只存在于个人经验、聊天记录或一次性脚本中。
- 页面变更后，可同步维护产品规则、自动化实现和回归用例，减少三者不一致。
- 为后续接口自动化、缺陷回归、探索式测试和用户培训提供统一知识来源。

需要注意：产品 Skill 只能沉淀已验证、已确认的通用业务规则，不应写入真实账号、密码、客户编号、房间数据或一次性测试数据；具体项目数据应继续保留在项目配置和测试数据文件中。
## 6. 方案优点

- 开发效率更高：业务人员提供步骤和验收标准后，AI 可快速生成初版代码和页面封装。
- 减少重复劳动：环境、账号、客户和业务参数分离后，同一套代码可切换多个环境。
- 维护成本更低：页面定位集中在 Page Object，页面变更时不必逐条修改测试用例。
- 覆盖复杂业务：可将金额计算、账期、状态流转和清理结果纳入自动断言。
- 问题定位更完整：失败时可保留截图、trace、日志和当前业务数据。
- 知识可以沉淀：人工确认后的流程、数据规则和定位方法可沉淀为代码、Excel、模板和公共规范。
- 相比接口自动化，可以验证真实用户操作链路、页面权限、菜单、弹窗、iframe 和前端展示结果。

## 7. 方案缺点和风险

- UI 自动化执行速度通常慢于接口自动化。
- 对页面结构、控件文本、iframe、异步加载和前端版本较敏感。
- 测试数据准备和清理复杂，失败后可能残留业务数据。
- 多用例并行执行时容易发生账期、房间、收费项和账号数据冲突。
- 浏览器、网络和服务器性能等外部因素会影响稳定性。
- AI 可能误解业务语义，生成表面可运行但业务断言错误的脚本。
- AI 可能生成不稳定定位器、过度使用固定等待或坐标点击。
- 过度依赖 AI 会导致代码缺少统一规范，增加维护成本。

关键约束：优先使用 role、label、稳定文本和限定容器定位；关键控件必须等待真实可见或可用；创建、作废、删除等操作必须有显式开关；生产环境默认只读。

## 8. 当前已实现的自动化场景

当前已形成 102 条入口级回归场景，按业务类型可简要归纳为：

- 周期类：覆盖账单中心和计费出账两类入口，共 44 条场景。
- 仪表类：覆盖账单中心和计费出账两类入口，共 24 条场景。
- 临时类：覆盖计费出账和临时台账两类入口，共 22 条场景。
- 押金类：覆盖计费出账和临时台账两类入口，共 12 条场景。

自动化场景主要验证：账单创建/出账、收费项选择、房间选择、账期、计费金额、账单状态、唯一编号生成，以及作废、删除和清理结果。

## 10. 后续推进计划

### 第一阶段：标准化

- 固化项目目录、命名、Page Object、Excel 字段和环境配置规范。
- 将账号密码、Cookie 和一次性测试数据与代码、Excel 分离。
- 统一失败截图、trace、HTML/JUnit 报告和实时日志格式。
- 统一创建、作废、删除和清理的安全开关规范。

### 第二阶段：稳定性治理

- 优先治理 iframe、房间树、收费项树、日期控件和固定表格等高频不稳定点。
- 为每个业务入口建立独立的创建、断言、清理和失败补偿流程。
- 建立环境冒烟用例，先验证登录、门户、业务 iframe 和关键菜单，再执行完整回归。
- 对账单、出账和临时台账建立数据门禁，避免脏数据影响后续批量执行。

### 第三阶段：持续回归

- 接入 Jenkins 或服务器 Docker 定时执行。
- 先采用串行执行保证数据安全，再根据数据隔离能力逐步分片或并行。
- 失败后自动归类为环境、数据、定位、产品缺陷和清理失败，减少无效重跑。
- 建立版本变更后的“页面验证—脚本修改—Excel 同步—规范同步”闭环。

## 11. 结论

当前方案采用“AI 辅助开发 + Python Playwright UI 执行 + pytest 用例管理 + Page Object 页面封装 + Excel/环境配置参数化”的技术路线。该方案能够减少手工编写和多环境适配工作，适合云收费中出账、账单生成、金额计算、状态流转和数据清理等复杂回归场景。

需要明确的是，多环境复用的关键不只是使用 AI，而是建立统一的配置、数据、页面封装、断言和清理规范。AI 可以提升脚本编写和问题分析效率，但业务规则确认、风险控制、数据安全和最终结果验收仍需要测试人员负责。
