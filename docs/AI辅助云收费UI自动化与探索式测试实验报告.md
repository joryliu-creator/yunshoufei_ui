# 人工主导、AI 辅助的云收费 UI 回归资产化实验报告

## 一、实验概况

| 项目 | 内容 |
|---|---|
| 实验名称 | 人工主导、AI 辅助的云收费回归资产化闭环实验 |
| 实验阶段 | 原型验证（PoC） |
| 实验周期 | 2026-08-07 至 2026-08-12 |
| 实验对象 | 天启标准云收费 Web 应用——账单中心及相关测试数据准备 |
| 实验环境 | 标准1环境，客户号 93537 |
| 技术组合 | 人工业务探索、Codex/AI 辅助记录与生成、Python、pytest、Playwright、Page Object、Excel 数据驱动 |
| 当前结论 | AI 独立探索陌生业务的效率低于熟练人工；“人工主导首次探索，AI完成结构化、代码生成与后续回归资产化”的路线可行 |

## 二、背景与问题

云收费属于天启平台的下游产品，出账依赖人员基础、房间基础、客户管理、房间收费设置、收费项和收费标准等多层前置数据。账单中心页面还存在多 iframe、异步弹窗、房间树、动态下拉、固定列表格、在线客服遮挡等复杂交互。

传统纯手工回归面临以下问题：

1. 账单创建、作废和删除步骤长，容易遗漏隐藏的“确定”、二次确认或通知选择。
2. 房间、收费项、收费标准、账期和账号权限组合多，测试数据难以统一维护。
3. 不同环境、客户和账号之间容易发生配置或登录态串用。
4. 页面显示值不一定等于最终业务结果，单纯“点击成功”不足以作为断言。
5. 测试经验往往停留在个人记忆中，难以快速转化为稳定的回归资产。

## 三、实验目标与假设

### 3.1 实验目标

验证能否利用 AI 完成以下闭环：

> 测试人员主导首次探索与业务判断 → AI 辅助记录和结构化 → 规则沉淀 → 生成 Playwright 脚本 → Excel 参数化 → 可重复执行与安全清理

### 3.2 实验假设

1. 对陌生业务，熟练测试人员主导首次探索比 AI 独立探索更高效。
2. AI 结合页面视觉、DOM 结构和测试人员提供的业务规则，适合辅助记录操作、补充检查点和整理页面规则，但不适合独立承担业务正确性判断。
3. 人工确认后的探索步骤可以沉淀为 Page Object 和 pytest 回归脚本。
4. Excel 可以作为业务测试数据的真实运行来源，降低代码修改和重复配置成本。
5. 通过安全开关、唯一编号和环境隔离，可控制创建、作废、删除等副作用风险。

本实验不以“AI 替代测试人员”为目标。业务规则判断、资金风险授权、异常结果确认和最终发布结论仍由测试人员负责。

## 四、实验方案

### 4.1 推荐的人机协作方式

实际试用发现，AI 单独进入陌生业务页面探索时，存在业务知识不足、每步需重新识别页面和工具调用等待等问题，整体速度明显慢于熟练人工。本实验因此将流程调整为：

1. 测试人员快速完成首次业务探索，并判断业务结果是否正确。
2. AI 同步观察或根据确认后的步骤，整理页面元素、操作顺序、检查点和异常分支。
3. 测试人员纠正隐含业务规则，例如“房间勾选后必须点击确定才查询收费项”。
4. AI 将已确认内容转换为 Excel 用例、Page Object、pytest 脚本和 Skill。
5. 后续重复回归由 Playwright 执行，AI 辅助分析截图、Trace 和失败日志。

AI 辅助观察仍不是单纯依赖截图识别，而是组合使用：

- **视觉观察**：识别弹窗、遮挡、房间树、表格和页面提示。
- **网页结构定位**：识别 iframe、按钮角色、输入框、可见弹层和目标数据行。
- **状态反馈分析**：观察点击前后收费项、标签、账单状态和列表结果的变化。
- **业务规则输入**：由测试人员确认项目、房间、收费项、账期、作废和删除的正确业务顺序。

### 4.2 角色分工

| 阶段 | 主责 | AI的作用 |
|---|---|---|
| 陌生业务首次探索 | 熟练测试人员 | 旁路记录、提示遗漏的检查维度 |
| 业务正确性判断 | 测试人员 | 提供基于页面状态的辅助信息 |
| 步骤与用例整理 | 人机协同 | 结构化步骤、预期、数据和风险 |
| 自动化脚本生成 | AI辅助、人工验收 | 生成 PO、pytest、配置和断言 |
| 重复回归 | Playwright | 批量执行；AI辅助归类失败 |
| 缺陷定性和发布结论 | 测试人员 | 汇总证据，不替代最终判断 |

### 4.3 自动化架构

```text
Excel 用例编号
    ↓
SCENARIO_ID
    ↓
收费场景配置 + 运行参数 + 账号角色
    ↓
Settings 配置加载
    ↓
pytest 业务场景
    ↓
Playwright Page Object
    ↓
天启门户 / 云收费账单中心
```

主要设计如下：

- 使用 Python、pytest 和 Playwright 同步 API。
- 页面定位集中在 Page Object，测试文件只编排流程和断言。
- 登录态按“环境/客户号/账号别名”隔离。
- 支持标准1、标准2、UAT、生产四类环境配置。
- 生产环境禁止执行带副作用标记的用例。
- 创建、清理、永久删除分别设置本地安全授权开关。
- Excel 不保存真实账号、密码、Token 或登录状态。

### 4.4 数据设计

Excel 数据职责被拆分为：

| 工作表 | 职责 |
|---|---|
| 用例清单 | 维护步骤、预期、账号角色和 `SCENARIO_ID` |
| 收费场景配置 | 维护项目、房间、收费项、收费标准、计算参数、减免和预期金额 |
| 运行参数 | 维护账期、日期、通知选择和作废原因 |
| 账号角色 | 维护账号别名、权限范围和可访问项目，不保存凭据 |

针对收费公式基准数据，额外形成：

- `房间导入模版.xlsx`：使用 `1001`～`1047` 的短房间编号。
- `房间收费标准映射表.xlsx`：维护房间编号与收费类型、原始公式、面积类型、建议收费标准名称的对应关系。
- 公式含“计费面积”时拆分为建筑面积、使用面积、收费面积三个测试场景。

## 五、实验过程与关键发现

### 5.1 负向观察：AI 独立探索效率不足

本次实际协作中确认：在 AI 尚不了解云收费业务时，单独让 AI 探索页面明显慢于熟练人工。主要原因包括：

- 不知道系统隐含业务规则，需要测试人员多次纠正。
- 每次操作前后需要重新读取页面结构并确认状态，工具调用存在等待时间。
- 创建、作废、删除属于高风险操作，AI 会进行更多安全确认。
- UI 能看到“发生了什么”，但不能仅凭视觉判断“业务结果是否正确”。

本阶段未记录双方精确耗时，因此只将“AI独立探索更慢”记为已观察结论，不虚构具体倍数或节省比例。下一阶段应使用同一组陌生场景分别记录“熟练人工独立探索”和“AI独立探索”的完成时间、纠正次数及有效发现数。

### 5.2 已验证主流程

实验以周期类账单为 Demo，流程包括：

1. 复用测试账号登录状态并进入云收费账单中心。
2. 选择目标项目并打开创建账单弹窗。
3. 清空房间输入框，展开房间树并勾选目标房间。
4. 点击房间树弹窗“确定”，等待系统查询房间收费项。
5. 设置应收日期、账期、收费类型、收费项和最晚缴款日。
6. 校验系统生成的计费期间属于目标账期。
7. 创建账单并在通知提示中选择“不需要”。
8. 记录本次生成的唯一账单编号。
9. 按唯一编号批量作废，填写原因并验证状态。
10. 再按同一编号批量删除，验证列表不再显示该账单。

### 5.3 探索阶段发现并沉淀的页面规则

| 编号 | 探索发现 | 风险 | 沉淀措施 |
|---|---|---|---|
| F01 | 正确登录地址为 `index.html#/login`，多写一个 `/` 会出现未登录响应 | 登录脚本进入错误页面 | 固化正确环境入口 |
| F02 | 登录状态可能同时依赖 Cookie 与 sessionStorage | 只保存 Cookie 后仍可能失效 | 同时保存并恢复两类状态 |
| F03 | 登录后存在多个异步公告或通知弹窗 | 遮挡菜单并导致误点击 | 按可见层级清理弹窗 |
| F04 | 项目选择框的只读 input 可能被显示文本覆盖 | 普通点击失败 | 定位外层组件及关联弹窗 |
| F05 | 房间勾选后必须点击房间树“确定” | 不确认就不会查询收费项 | 将“勾选”和“确定”拆为独立步骤及断言 |
| F06 | 收费项依赖房间确认和收费类型选择后异步加载 | 固定等待不稳定 | 使用可重试的可见性/唯一性断言 |
| F07 | 页面可能显示选择了7月，但实际计费期间进入8月 | 生成错误账期账单 | 提交前断言实际计费期间 |
| F08 | Element UI 固定列把同一业务行拆成多张表 | 可能选错行或读错状态 | 以唯一账单编号作为权威定位 |
| F09 | 在线客服可能遮挡右侧操作区域 | 无法点击“更多”等按钮 | 操作前收起客服，必要时清理遮挡 |
| F10 | 作废后仍需重新勾选并执行批量删除 | 只作废未完成数据清理 | 作废、状态断言、删除拆成独立阶段 |
| F11 | 删除确认层未必具有标准 ARIA dialog | 常规弹窗定位失效 | 按确认语义和最近按钮容器定位 |

这些规则已经进入 Page Object、测试步骤或项目 Skill，后续新增场景可以复用。

## 七、创新点与业务价值

### 7.1 创新点

1. **人工探索与自动化资产化连成闭环**：测试人员负责高效探索和业务判断，AI负责把确认后的知识转成结构化用例、代码和规则。
2. **业务规则资产化**：房间树确认、计费期间校验、固定列表格、异步弹窗等经验从个人记忆变为团队可复用 Skill。
3. **Excel 与代码打通**：测试人员继续使用熟悉的 Excel 维护业务数据，执行代码直接读取，避免文档和脚本两套数据漂移。
4. **复杂依赖数据结构化**：用短房间编号和收费标准映射表管理47组公式场景，兼顾基础模块校验与业务可追溯性。
5. **风险操作可控**：创建、作废、永久删除均有显式授权，清理按本次唯一账单编号执行，生产环境强制禁用副作用。

### 7.2 预期价值

- 缩短人工已确认场景转化为 UI 回归脚本的整理和编码时间。
- 降低隐藏确认步骤、错误账期和误删测试数据的风险。
- 提高不同环境、客户和账号测试数据的可维护性。
- 把人工探索发现持续转化为回归用例，减少问题重复出现。
- 为后续覆盖缴费、退款、仪表、押金和临时收费流程提供统一底座。

以上为预期价值。当前尚未形成多轮人工基线与自动化运行数据，暂不宣称具体节省百分比。

## 八、局限与风险

1. 当前仅完成1条业务端到端脚本，尚不足以代表整个云收费模块。
2. AI 独立探索陌生业务的速度低于熟练人工，不应把首次探索效率作为当前方案的优势。
3. 页面结构变化、异步加载和第三方遮挡仍可能造成脚本维护成本。
4. 上游基础、客户管理和收费设置前置数据仍需跨产品协同或稳定基准数据。
5. 资金类操作必须保留人工授权，不能追求完全无人值守。
6. AI 可能误解业务语义，测试人员的确认与结果复核不可省略。
7. 当前缺少人工执行时长、资产转化时长、重复运行稳定性和缺陷命中率的正式对照数据。

## 九、下一阶段实验计划

建议用2～4周完成可量化验证：

### 阶段一：扩大样本

- 从约190条主流程用例中选择10～20条稳定、数据可控的 P0/P1 场景。
- 覆盖周期类、临时类、押金类、仪表类以及多账号业务。
- 每条场景分别记录首次人工探索、AI独立探索、人工整理脚本、AI辅助资产化所需时间；AI独立探索仅作为能力基线，不作为推荐生产流程。

### 阶段二：连续运行

- 在标准1环境连续执行至少10轮。
- 统计首轮通过率、重复运行通过率、非业务失败率和平均修复时间。
- 对失败原因分类：产品缺陷、脚本缺陷、环境/数据问题、AI 理解偏差。

### 阶段三：价值评估

建议采集以下指标：

| 指标 | 计算方式 |
|---|---|
| 首次探索效率差异 | 对比熟练人工与AI独立探索的耗时、纠正次数、有效发现数 |
| 资产转化效率提升 | `(人工整理编码耗时-AI辅助资产化耗时)/人工整理编码耗时` |
| 重复运行稳定性 | `无脚本问题通过次数/总运行次数` |
| 探索发现转化率 | `已转成断言或回归脚本的发现数/有效探索发现数` |
| 缺陷命中率 | `确认产品缺陷数/执行场景数` |
| 数据准备耗时下降 | 对比使用映射模板前后的准备时长 |
| 维护成本 | 页面变更后修复脚本的平均人时 |

### 阶段四：团队复用

- 让另一名测试人员只依据 Excel 模板和 Skill 新增1～2条场景。
- 观察是否能在较少口头指导下完成，以验证方案是否真正可复制。

## 十、实验结论

本次实验同时得到正向和负向结论：AI 独立探索陌生业务时，由于缺少领域知识和存在交互工具延迟，效率低于熟练人工；但在测试人员完成业务探索并确认规则后，AI适合承担步骤结构化、脚本生成、测试数据整理、规则沉淀和失败分析，将一次人工探索转化为可维护的自动化资产。

当前成果已经超过概念演示，具备可运行框架、业务脚本、数据模型、安全控制和团队复用说明；但覆盖规模和量化数据仍处于 PoC 阶段。建议将项目定位为：

> **人工主导、AI 辅助的云收费回归资产化闭环 PoC**

下一步不宜继续堆砌功能，应优先用10～20条场景、10轮连续运行和人工对照工时验证效率、稳定性和缺陷发现价值，再决定是否推广到其他测试组。

## 附录A：主管汇报摘要

实际试用发现，AI单独探索陌生业务既不懂隐含规则，速度也慢于熟练人工，所以我们没有把方向定位成“AI替代测试”。调整后的方案是：测试人员主导首次探索和业务判断，AI把确认后的过程整理成 Excel 用例、Python Playwright 脚本和可复用 Skill，后续由代码重复回归。当前已跑通账单创建、批量作废和批量删除主流程，沉淀了多 iframe、房间树确认、异步弹窗、计费期间校验、唯一账单定位等规则，并建立四环境、多账号和生产安全保护。静态验证33项全部通过，另整理47组收费公式基准数据。下一步选择10～20条核心场景，重点量化“人工探索后转成自动化资产”的效率和重复回归稳定性。

## 附录B：5分钟汇报结构

1. **1分钟——痛点**：云收费链路长、数据依赖多、页面交互复杂、回归重复。
2. **1分钟——真实结论与方案**：AI独立探索较慢；采用人工探索 + AI资产化 + Playwright回归 + Excel数据驱动。
3. **1分钟——演示**：展示有头模式执行“创建账单 → 作废 → 删除”。
4. **1分钟——成果**：展示框架、Excel配置、47组公式映射和安全开关。
5. **1分钟——计划**：10～20条场景、10轮运行、与人工耗时对照，再决定推广。
